# Localization

## Purpose
Every text the player reads, in Turkish or English. A text in code is its own key: the Turkish
(or, for a few lobby lines, English) source is looked up in the tables and the current language's
translation comes back, or the source itself when there is none, so nothing is ever blank.

## Concepts
localization, language, translation, Türkçe, English, ILocalizationService, TextLocalizer, csv

## Decisions
- Source text as key, not ids. Code and config assets keep reading naturally, and a missing row
  shows the source instead of an id. Changing a source text means changing its row's key too.
- Each module ships its own table at `<Module>/Resources/Localization/<Module>.csv`
  (`key,tr,en`), the way each module ships its own audio bank. All tables are read once, at the
  first lookup. An empty cell falls back to the key.
- Formatted lines keep their placeholders in the key - `DALGA {0} TEMİZLENDİ` - and colour tags
  stay outside the key wherever the line allows it.
- The language is the device's at first run (Turkish devices get Turkish, every other English),
  then whatever the player picked, kept in PlayerPrefs under `LANGUAGE`.
- A View cannot be injected and a Mediator is injected with its View only, so the Command that
  opens a screen fills the screen's `TextLocalizer` from the service (`screen.Localizer.Use(...)`).
  Labels bound through it are rewritten whenever it is refilled - the lobby's language button
  refills the open lobby. A zone's sign is filled by `LocalizeZoneCommand` after the zone registers.

## Known gaps
- A row is found by exact text: a source line edited in code and not in its table falls back to
  the source until the table is updated. The Editor warns once per missing key.
